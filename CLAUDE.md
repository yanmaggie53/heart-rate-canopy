# Heart Rate Canopy

Project context for Claude Code. Ideation and planning happen in a separate Claude chat; this repo is where the code lives. Read this file before touching anything.

## What this is

A piece for Maggie's Advanced New Media class, shown in a gallery where visitors use it unattended. A fabric canopy with two or three handmade cushions inside. Addressable fairy lights inside the canopy change color based on the sitter's heart rate. The goal for the sitter is to bring their heart rate down toward a calm target. Theme is unwinding in the middle of a busy life, with physiological data as the way to bring embodied experience into the piece.

Builds on two earlier projects by the same author that turned physiological data into a material output (MEmento, and an EEG-driven embroidery machine).

## Pipeline

```
heart rate sensor --(Bluetooth)--> controller --(data line)--> addressable LED fairy string
```

Two stages:

1. **Now (web prototype, `web/index.html`).** A single HTML page reads heart rate over Web Bluetooth (Chrome or Edge, on https or localhost) from any device with the Heart Rate Service, today the canopy board's relay "Canopy" (it passes on the armband's reading, so the page and the lights show the same number; confirmed 2026-11-20 with the page served from localhost), or the armband itself while the board isn't holding it, or HeartCast relaying the Apple Watch, and paints the screen as a stand-in canopy; Pulsoid's websocket stays as a fallback under "Use Pulsoid instead" (added 2026-11-13). HeartCast must be open on the iPhone screen while the chooser is up, or the list stays empty. Chrome on macOS forgets a picked device about 3 minutes after it last saw it advertise, so a later drop can't be retried and the page asks for a new pick instead. Hosted at https://yanmaggie53.github.io/heart-rate-canopy/ by GitHub Pages (`.github/workflows/pages.yml` publishes the `web/` folder on every push to main); it also runs as a local file by double-clicking. The Pulsoid websocket is wss and is not restricted by page origin (a handshake probe from a github.io origin was rejected for the token, not the origin), so the hosted page can use it. An earlier note here claimed only a local page could; that was wrong. Since 2026-11-20 the page honors the skin-contact bits of a reading ("nobody there" from the board, or a sensor off the skin, resets the session), counts a reading as missing after a few of the source's usual gaps (6 s for the armband, up to 20 s for HeartCast; from a source that says who is there, such as the board, it trusts that and waits 20 s for plain silence) and then shows the same dim, ember-warm waiting look as the lights (still breathing the cue) and starts a new session, and also starts a new session when test mode turns on or off. To try a branch's page with Bluetooth before it is on main, serve it from localhost (`python3 -m http.server 8732 --bind 127.0.0.1 --directory web`, or a preview entry in the local, uncommitted `.claude/launch.json`); a `data:` or file page in the browser pane is not a secure context.
2. **Later (gallery piece, `firmware/`, started 2026-11-07 with a light test).** ESP32 reads the armband directly over Bluetooth (standard Heart Rate Service 0x180D, characteristic 0x2A37) and drives WS2812B fairy lights. No laptop in the gallery: the board can run from a USB wall charger, since the S3's USB serial drops output instead of blocking when no computer reads it. The armband is a COOSPO HW807 (optical, worn on the forearm), working end to end on 2026-11-20 with no code change needed: it advertises as "COOSPO HW807", the board finds and connects to it about 1 s after booting and gets a reading every second. Checked against the author's Apple Watch twice the same day: within about 2 bpm, the watch lagging slightly. `canopy.cpp` connects only to a device whose name starts with `TARGET_NAME = "COOSPO"`, so it never grabs a phone running HeartCast; set it to "" to go back to the first heart rate device heard. Before the Coospo, an iPhone app that relays the Apple Watch's reading as a standard Bluetooth heart rate monitor (HeartCast, confirmed working 2026-11-10; HR Broadcast and HeartBLE are alternatives) stood in for it, and still can. Pulsoid can't do this; its path is watch to phone to website.
   Since 2026-11-20 (tested on the board with the armband the same day) the canopy sketch also: relays to the web page, advertising its own Heart Rate Service as `RELAY_NAME = "Canopy"` every 250 to 500 ms and notifying every reading the lights use, plus "nobody there" (contact bits supported but not detected, rate 0) every 2 s while the lights show the waiting look (`RELAY_TO_WEB = false` turns it off); hands readings from the NimBLE task to `loop()` through a FreeRTOS queue (`hrQueue`) so the smoother and session are only touched from one task; counts a reading as missing after 4 of the sensor's usual gaps, clamped to 6..20 s (`staleMs()`), instead of a fixed 20 s, but waits the full 20 s while the armband's link is down or within 3 s of it coming back (a reason-520 drop takes 5 to 7 s to recover and doesn't mean the sitter left); supports an optional seat switch (`SEAT_PIN`, see the decision below) and serial commands `sit`, `leave`, `noseat` and `status` to pretend one; asks the armband for a 30 to 50 ms connection interval and a 4 s supervision timeout (it was 15 ms and 1.5 s); and prints the armband's battery level on connect if it offers the Battery Service. The armband's signal at the board ranges from about -55 to -93 dBm on the wearer's arm a meter or two away, depending on how the arm blocks it; at the weak end readings came in fits until the arm moved.
   What the HW807 does and doesn't do (measured 2026-11-20): it takes one Bluetooth connection at a time and stops advertising once connected, so while the board holds it, Chrome's chooser doesn't list it and the web page can't read it directly. It sends no skin-contact flag (flags bit 2 clear, so the sketch's "off the skin" handling never fires for it) and no RR intervals, so no true per-beat pulse from it. It occasionally drops the link (reason 520, supervision timeout) and the board reconnects within about a second. Taken off the arm and left switched on, it keeps sending invented readings for up to about a minute, drifting upward (60 to 73 in one test, 60 to 90 over ~50 s in another), then stops sending while staying connected (once, later, it went quiet as soon as it came off instead). The board then went to the waiting look 20 s later, 6 s since the change below. So without a seat sensor the lights still show a rising heart rate for up to a minute after a visitor leaves, and a visitor who puts it on within that time doesn't get a fresh start; a seat sensor fixes both (tested with the pretend seat: 4 s after `leave` the lights and the page went to the waiting look). Put back on after the drift, it read 90 and slid to the real ~60 over about 20 s (one observation; it may start from its last made-up value), so a new sitter's first 20 s or so can read high.

## Decisions already made

- Sensor for the gallery is an optical arm band because strangers will put it on: a COOSPO HW807 (in hand since 2026-11-20) in place of the Polar Verity Sense planned earlier. A chest strap (Polar H10 or similar) is the alternative for the author's own testing and gives beat timing. Apple Watch is only for prototyping (one reading every ~5 s, no Bluetooth broadcast).
- Lights are WS2812B / NeoPixel addressable fairy strings on thin wire, 3-wire (5V, data, ground). Two-wire strings don't work with standard libraries. Separate 5V supply, not the ESP32's USB.
- Controller is an ESP32 dev board. Use NimBLE-Arduino for Bluetooth (the stock ESP32 BLE library crashes on Polar H10/H9) and FastLED or Adafruit NeoPixel for the lights.
- Color: warm throughout, and warmer as the heart slows (decided 2026-11-20, replacing a fixed dusk palette chosen earlier the same day, which had replaced the purple-to-red hue scale of 2026-10-27). The author wants a feedback loop: warm light helps the sitter feel calm from the moment they sit down, and as their heart rate drops the light gets warmer still, which should help it drop further. So every color is warm, on a gradient from the calmest end (deep ember) to the most stirred (pale warm white), and the canopy's place on it is the same t that sets brightness (below), eased the same way: a slowing heart makes the canopy dimmer and deeper amber, like a fire burning down; at the sitter's start it is honey gold. Classmates had said that a color standing for a number made them watch the number and got them nervous; because t is measured from each sitter's own start, no color stands for a fixed bpm, and the range is narrow and all warm, so it reads as atmosphere rather than a gauge. Each light sits a little ahead of or behind the others on the gradient (`SPREAD` 0.12), so a few neighboring warm tones show at once. Palettes are in `firmware/include/palette.h` (stops must match `PALETTES` in the web page): hearth (ember, amber, honey, warm white; the default, `CANOPY_PALETTE`), coral (deep coral to peach white) and candle (amber to candle white, a narrower range), compared under Tuning in the web page or on the string by typing a palette's name into the canopy sketch's serial monitor. The waiting look (nobody sitting) is the ember end, dim and breathing slowly. The stops are screen colors, so on the string they are gamma-decoded (2.2) before brightness is applied (`ledColor` in palette.h); sent as they were, ember came out light orange and warm white nearly white. Brightness stays linear on the LEDs, and the web page matches it by drawing each light with alpha^(1/2.2). Each light is rounded to 8 bits once (`BRIGHTNESS` is applied per light, `FastLED.setBrightness(255)`); FastLED's temporal dithering is left off, since it only runs above 100 fps and at these low values its pattern could shimmer.
- Heart rate drives brightness (and, through the same t, the warmth above), measured from where the sitter started, not on a fixed bpm scale (the fixed scale of 2026-10-27 existed so every bpm had its own color, and that reason is gone; someone resting at 85 should be able to dim the canopy as much as someone at 60). Start = average of the sitter's first 30 s of readings (the running average until then). t = (hr - (start - 12)) / (12 + 6), clamped 0..1; level = 0.2 + 0.8·t. So the lights sit at about three quarters when someone sits down, reach the dimmest (20%, a soft glow, not darkness) 12 bpm below the start, and full brightness 6 above. The rate is a 10 s rolling average (raw values jitter by 2 to 5 bpm even at rest), and the shown level eases toward its target with a 4 s time constant when dimming and 12 s when brightening, so calm is rewarded at once and a cough doesn't visibly punish anyone. All of these are adjustable under Tuning and at the top of `firmware/include/mapping.h`. A stepped mode (the rate rounded to every N bpm before mapping) stays as an option to compare. A new sitter starts whenever the canopy decides nobody is there (see "Who is there" below), or with New sitter in the web page or `new` in the serial monitor. The board owns the session: whenever it starts a new sitter it tells the web page ("nobody there" over the relay), and every relayed reading carries the board's start (tenths of a bpm in the Heart Rate Measurement's Energy Expended field, flags bit 3), which the page uses instead of its own, so a page that connects partway through dims and warms exactly like the lights. The page reads that field only from a device named Canopy. One observation from 2026-11-20 (not confirmed): an armband put back on after its off-arm drift read 90 and slid to the real ~60 over about 20 s. If that is typical, the first-30-s average overstates where a visitor started, and leaving the first ~20 s of a new sitter out of the start may be worth trying (not done).
- Test mode (under Tuning in the web page) feeds an exact fake reading from a slider, once a second and whenever the slider moves, so the dimming can be checked without a watch: its first 30 s set the start, then sliding below it dims the canopy. Connecting a live heart rate (Bluetooth or Pulsoid) turns it off and starts a fresh session.
- The lights carry a slow breathing cue, not the heart rate (decided 2026-11-20, replacing brightness that breathed at the current heart rate). The whole canopy swells for 4 s and fades for 6 s, about six breaths a minute with a longer out-breath, the pace slow-breathing studies use: slow breathing is the one thing in the evidence that reliably calms people within minutes, and light that changes with color or brightness alone does little by itself. The sitter can breathe along with it without being told to count, and it keeps the same pace whether or not anyone is sitting, so the empty canopy invites a slow breath too. It doesn't follow the heart rate, which now shows only as brightness and warmth, so a fast heart no longer reads as flicker. `breathAt` (half-cosine rise and fall, `INHALE_S`, `EXHALE_S`) and `swellFor` (0.5 with the breath out, 0.9 in, the same depth at every level so it stays easy to follow at the calm end) are in palette.h, mirrored in the web page, where "breathe in/out for" under Tuning tries other paces. The per-light twinkle gets shallower as the canopy calms (`twinkleFor`), so a calm canopy is still apart from the breath. The gallery sign could say: breathe in as the lights swell, out as they fade.
- Who is there (decided 2026-11-20): the armband can't tell, so presence comes from a seat switch in the cushion when one is fitted, and from the readings alone when not. With a switch, readings only count while someone sits (pressed for `SIT_MS` = 1 s starts a new sitter, released for `LEAVE_MS` = 4 s, so shifting weight doesn't end a session, goes to the waiting look). Recommended switch for handmade cushions: a pressure mat switch (two wires, closes under weight, no tuning) under the cushion's top layer; a force sensitive resistor (FSR, e.g. a square 40 mm one) wired the same way should also work with the board's internal pull-up (untested), and a soft switch sewn from two layers of conductive fabric separated by holed foam is the craft version. Wiring for any of them: one wire to the header pin labeled 5 (next to 4, where the lights' data wire goes), the other to a pin labeled GND, then set `SEAT_PIN = 5` in `canopy.cpp` and upload. Several cushions: wire their switches side by side to the same two pins (any one pressed counts as someone there).
- Heart rate is physiological data. The gallery needs a sign saying it's measured and whether it's stored. While the relay is on (`RELAY_TO_WEB`), anyone nearby with a Bluetooth app can read the sitter's heart rate from "Canopy", as they could from the armband itself before the board connects; say so on the sign or turn the relay off for the show. Logged data is anonymous (no names, no timestamps that identify a person).
- Look of the web stand-in: the field is pure black and only the fairy lights carry color (a soft halo around each, as through fabric). One typeface for everything, Gaegu (Google Fonts), a handwritten face with an uneven baseline, all lowercase, with a faint glow in the lights' current warmth, stronger as they brighten. Sizes stay close together: body and controls 15 to 17 px, the reading capped at 90 px (it was 180). Cozy, not sharp. Decided 2026-10-30 after trying Fraunces + Instrument Sans, Fredoka + Nunito and Young Serif; the author wants handwritten, uneven, and no big size jumps.

## Code conventions

- Keep the mapping logic (`levelT`, `levelFor`, `easeLevel`, the start rate, smoothing, `lightPos`, and the palette stops) separate from presentation. It is the one piece that moves from the web prototype to the ESP32 unchanged in behavior.
- Plain, dependency-free HTML/JS for the web prototype. No build step.
- Never commit a Pulsoid token. The page keeps it in localStorage only.
- Firmware in Arduino/PlatformIO C++, with the pin numbers, LED count and supply current written at the top of the sketch.
- `firmware/` is one PlatformIO project: each sketch is a `.cpp` in `src/` with its own `[env:...]` in `platformio.ini` (selected by `build_src_filter`; `canopy` is the default, `pio run -e light_test -t upload` for the wiring test), the mapping and smoothing live in `include/mapping.h`, matching the web page, and the palettes both sketches share are in `include/palette.h`. Bluetooth is NimBLE-Arduino 2.x (Arduino core 3.3 here), and connecting is done from `loop()`, never inside a NimBLE callback. Readings go the same way: `onNotify` only puts each one on a FreeRTOS queue that `loop()` drains, so only `loop()` touches the session (smoother, start rate). Code is edited in Cursor or here and built and uploaded with the `pio` command line; Arduino IDE isn't used. The board is an ESP32-S3 dev board with an ESP32-S3-WROOM-2 module and two micro-USB ports, USB and UART. esptool reads it (2026-11-07) as ESP32-S3 rev v0.2, 32 MB octal flash and 16 MB PSRAM at 1.8 V, so a WROOM-2 N32R16V. `platformio.ini` sets `board = esp32-s3-devkitc-1` with `board_build.arduino.memory_type = opi_opi` (without it the board won't boot), and GPIO 35 to 37 are off limits. Flash size stays at the 8 MB default, which is plenty.
- The laptop goes on the port labeled **USB** (the S3's own USB, `/dev/cu.usbmodem*`, no driver), and `-DARDUINO_USB_CDC_ON_BOOT=1` sends `Serial` there. On this port DTR/RTS are wired to reset and boot: esptool's usual hard reset after an upload, or a serial tool that drops DTR or RTS, lands the board in download mode ("waiting for download") instead of running the sketch. So `board_upload.after_reset = watchdog-reset`, and anything that reads the port must open it with DTR and RTS left asserted (pyserial's default). The USB serial doesn't buffer, so lines printed before the monitor opens are lost: that is why the canopy sketch repeats its status every 20 s while scanning. If the board is ever stuck in download mode, hold BOOT, tap RST, release BOOT, upload again, or run esptool with `--before no-reset --after watchdog-reset`.
- The board needs a micro-USB cable that carries data. The first one tried only charged: the board lit up but the Mac never saw a USB device. If an upload says "No serial data received", check that a `/dev/cu.usbmodem*` port exists before anything else; without one, PlatformIO used to pick a Bluetooth headphone port (`upload_port` now names the port pattern).
- On the author's Mac (macOS 13), PlatformIO is installed in its own Python environment at `~/.platformio/penv`, not with Homebrew: Homebrew has no prebuilt packages for macOS 13 and compiles everything from source.
