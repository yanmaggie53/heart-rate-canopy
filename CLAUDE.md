# Heart Rate Canopy

Project context for Claude Code. Ideation and planning happen in a separate Claude chat; this repo is where the code lives. Read this file before touching anything.

## What this is

A piece for Maggie's Advanced New Media class, shown in a gallery where visitors use it unattended. A fabric canopy with two or three handmade cushions inside. Addressable fairy lights inside the canopy change color based on the sitter's heart rate. The goal for the sitter is to bring their heart rate down toward a calm target. Theme is unwinding in the middle of a busy life, with physiological data as the way to bring embodied experience into the piece.

Builds on two earlier projects by the same author that turned physiological data into a material output (MEmento, and an EEG-driven embroidery machine).

## Pipeline

```
heart rate sensor --(Bluetooth)--> controller --(data line)--> addressable LED fairy string
```

Two stages:

1. **Now (web prototype, `web/index.html`).** A single HTML page reads heart rate over Web Bluetooth (Chrome or Edge, on https or localhost) from any device with the Heart Rate Service, today HeartCast relaying the Apple Watch, and paints the screen as a stand-in canopy; Pulsoid's websocket stays as a fallback under "Use Pulsoid instead" (added 2026-11-13). HeartCast must be open on the iPhone screen while the chooser is up, or the list stays empty. Chrome on macOS forgets a picked device about 3 minutes after it last saw it advertise, so a later drop can't be retried and the page asks for a new pick instead. Hosted at https://yanmaggie53.github.io/heart-rate-canopy/ by GitHub Pages (`.github/workflows/pages.yml` publishes the `web/` folder on every push to main); it also runs as a local file by double-clicking. The Pulsoid websocket is wss and is not restricted by page origin (a handshake probe from a github.io origin was rejected for the token, not the origin), so the hosted page can use it. An earlier note here claimed only a local page could; that was wrong.
2. **Later (gallery piece, `firmware/`, started 2026-11-07 with a light test).** ESP32 reads the armband directly over Bluetooth (standard Heart Rate Service 0x180D, characteristic 0x2A37) and drives WS2812B fairy lights. No laptop in the gallery: the board can run from a USB wall charger, since the S3's USB serial drops output instead of blocking when no computer reads it. The armband is a COOSPO HW807 (optical, worn on the forearm), working end to end on 2026-11-20 with no code change needed: it advertises as "COOSPO HW807", the board finds and connects to it about 1 s after booting and gets a reading every second. Checked against the author's Apple Watch twice the same day: within about 2 bpm, the watch lagging slightly. `canopy.cpp` connects only to a device whose name starts with `TARGET_NAME = "COOSPO"`, so it never grabs a phone running HeartCast; set it to "" to go back to the first heart rate device heard. Before the Coospo, an iPhone app that relays the Apple Watch's reading as a standard Bluetooth heart rate monitor (HeartCast, confirmed working 2026-11-10; HR Broadcast and HeartBLE are alternatives) stood in for it, and still can. Pulsoid can't do this; its path is watch to phone to website.
   What the HW807 does and doesn't do (measured 2026-11-20): it takes one Bluetooth connection at a time and stops advertising once connected, so while the board holds it, Chrome's chooser doesn't list it and the web page can't read it directly. It sends no skin-contact flag (flags bit 2 clear, so the sketch's "off the skin" handling never fires for it) and no RR intervals, so no true per-beat pulse from it. It occasionally drops the link (reason 520, supervision timeout) and the board reconnects within about a second. Taken off the arm and left switched on, it keeps sending invented readings for up to about a minute, drifting upward (60 to 73 in one test, 60 to 90 over ~50 s in another), then stops sending while staying connected; the board goes to the waiting look `STALE_MS` (20 s) later. So the lights show a rising heart rate for roughly a minute after a visitor leaves, and a visitor who puts it on within that time never gets a fresh start. That is a reason for next task 5 (a cushion button or pressure sensor).

## Decisions already made

- Sensor for the gallery is an optical arm band because strangers will put it on: a COOSPO HW807 (in hand since 2026-11-20) in place of the Polar Verity Sense planned earlier. A chest strap (Polar H10 or similar) is the alternative for the author's own testing and gives beat timing. Apple Watch is only for prototyping (one reading every ~5 s, no Bluetooth broadcast).
- Lights are WS2812B / NeoPixel addressable fairy strings on thin wire, 3-wire (5V, data, ground). Two-wire strings don't work with standard libraries. Separate 5V supply, not the ESP32's USB.
- Controller is an ESP32 dev board. Use NimBLE-Arduino for Bluetooth (the stock ESP32 BLE library crashes on Polar H10/H9) and FastLED or Adafruit NeoPixel for the lights.
- Heart rate is mapped to hue continuously, not in bins, with a rolling average over the last 5 to 10 s, because raw values jitter by 2 to 5 bpm even at rest and a stepped palette strobes. A stepped mode (new color every N bpm) stays available as an option to compare.
- The scale is fixed in bpm, not relative to the sitter. Visitors are seated, neither sleeping nor exercising, and mostly students, so a realistic seated range reads the same for everyone and every bpm has its own color. Defaults: floor 55 bpm, ceiling 95 bpm, both adjustable under Tuning. Mapping: t = (hr - floor) / (ceiling - floor), clamped 0..1. Decided 2026-10-27, replacing the per-sitter scale (baseline from the first 30 s, calm target = baseline - 20). The first-30-s average is still kept as "started at", but it only feeds the line under the reading.
- Color runs down the wheel from purple at the floor (hue 280) through blue, cyan, green, yellow and orange to red at the ceiling (hue 0), continuously: hue = 280·(1 - t). With the default range that is 7 degrees per bpm, so a change of one bpm is a visible shift. Decided 2026-10-27, replacing the blue-to-magenta scale of 2026-10-26.
- Test mode (under Tuning in the web page) feeds an exact fake reading from a slider, once a second and whenever the slider moves, so each color can be checked without a watch. Connecting a live heart rate (Bluetooth or Pulsoid) turns it off and starts a fresh session.
- Lights "breathe" (brightness oscillates) at the current heart rate, so a fast heart reads as flicker and a slow one as breathing. With the H10's beat timing this can become a true per-beat pulse.
- Heart rate is physiological data. The gallery needs a sign saying it's measured and whether it's stored. Logged data is anonymous (no names, no timestamps that identify a person).
- Look of the web stand-in: the field is pure black and only the fairy lights carry color (a soft halo around each, as through fabric). One typeface for everything, Gaegu (Google Fonts), a handwritten face with an uneven baseline, all lowercase, with a faint glow in the current light color. Sizes stay close together: body and controls 15 to 17 px, the reading capped at 90 px (it was 180). Cozy, not sharp. Decided 2026-10-30 after trying Fraunces + Instrument Sans, Fredoka + Nunito and Young Serif; the author wants handwritten, uneven, and no big size jumps.

## Code conventions

- Keep the mapping logic (`targetT`, `hueFor`, smoothing, floor and ceiling) separate from presentation. It is the one piece that moves from the web prototype to the ESP32 unchanged in behavior.
- Plain, dependency-free HTML/JS for the web prototype. No build step.
- Never commit a Pulsoid token. The page keeps it in localStorage only.
- Firmware in Arduino/PlatformIO C++, with the pin numbers, LED count and supply current written at the top of the sketch.
- `firmware/` is one PlatformIO project: each sketch is a `.cpp` in `src/` with its own `[env:...]` in `platformio.ini` (selected by `build_src_filter`; `canopy` is the default, `pio run -e light_test -t upload` for the wiring test), the mapping and smoothing live in `include/mapping.h`, matching the web page, and the hue-to-RGB conversion both sketches share is `include/hue_rgb.h`. Bluetooth is NimBLE-Arduino 2.x (Arduino core 3.3 here), and connecting is done from `loop()`, never inside a NimBLE callback. Code is edited in Cursor or here and built and uploaded with the `pio` command line; Arduino IDE isn't used. The board is an ESP32-S3 dev board with an ESP32-S3-WROOM-2 module and two micro-USB ports, USB and UART. esptool reads it (2026-11-07) as ESP32-S3 rev v0.2, 32 MB octal flash and 16 MB PSRAM at 1.8 V, so a WROOM-2 N32R16V. `platformio.ini` sets `board = esp32-s3-devkitc-1` with `board_build.arduino.memory_type = opi_opi` (without it the board won't boot), and GPIO 35 to 37 are off limits. Flash size stays at the 8 MB default, which is plenty.
- The laptop goes on the port labeled **USB** (the S3's own USB, `/dev/cu.usbmodem*`, no driver), and `-DARDUINO_USB_CDC_ON_BOOT=1` sends `Serial` there. On this port DTR/RTS are wired to reset and boot: esptool's usual hard reset after an upload, or a serial tool that drops DTR or RTS, lands the board in download mode ("waiting for download") instead of running the sketch. So `board_upload.after_reset = watchdog-reset`, and anything that reads the port must open it with DTR and RTS left asserted (pyserial's default). The USB serial doesn't buffer, so lines printed before the monitor opens are lost: that is why the canopy sketch repeats its status every 20 s while scanning. If the board is ever stuck in download mode, hold BOOT, tap RST, release BOOT, upload again, or run esptool with `--before no-reset --after watchdog-reset`.
- The board needs a micro-USB cable that carries data. The first one tried only charged: the board lit up but the Mac never saw a USB device. If an upload says "No serial data received", check that a `/dev/cu.usbmodem*` port exists before anything else; without one, PlatformIO used to pick a Bluetooth headphone port (`upload_port` now names the port pattern).
- On the author's Mac (macOS 13), PlatformIO is installed in its own Python environment at `~/.platformio/penv`, not with Homebrew: Homebrew has no prebuilt packages for macOS 13 and compiles everything from source.

## Next tasks

2. Run `firmware/src/light_test.cpp` on the real string and set the pin, LED count, color order and supply current it confirms. Done so far: it uploads and runs on the board, and its serial output prints hue 280 at 55 bpm down to 0 at 95, 7 degrees per bpm, the same as the web page (2026-11-07). On 2026-11-10 the string was wired per the sheet below and lights up, and the color-order stage seemed to show red, green, blue in order, so `COLOR_ORDER = GRB` was set. That was a misread: on 2026-11-20 the live canopy showed pink at about 70 bpm (should be cyan), and sending pure colors from the serial test mode showed red as green and blue as red, so the string is BGR (`COLOR_ORDER = BGR` in both sketches, confirmed red and blue on the string after). A wrong order still cycles through three colors in the light test, so watch which comes first. The string has 200 lights (`NUM_LEDS = 200`, set and uploaded 2026-11-10). `SUPPLY_MA` is 1000 as a safe placeholder until the adapter's rating is known; set it to about two thirds of the rating, since FastLED counts ~43 mA per white light against ~60 mA real. 200 lights at full white would be ~12 A, so the limiter always matters, and on thin fairy wire the far end may need power injected (5V and GND only) at higher brightness. Wiring schematic (rev B, 2026-11-10: a minimal Fritzing-style schematic with six notes, at the author's request; the board is drawn as it sits with USB at the bottom, J1 on the left; reviewed for electrical, pinout and layout mistakes): https://claude.ai/artifact/Qi5ZjndLqf86Yaz3ZubQvX (private to the author). It also records which header pins to leave alone on this board: 35 to 37 (memory), 19 and 20 (the USB port's data lines), 47 and 48 (1.8 V on this module).
3. Test `firmware/src/canopy.cpp` with a real heart rate. Written 2026-11-10 and running on the board: a NimBLE client that scans for any device with the Heart Rate Service, subscribes to 0x2A37 and reconnects when dropped; the 5 s rolling average and optional stepped mode from the web page (now in `include/mapping.h`); FastLED breathing at the heart rate with per-light twinkle and eased hue; a dim slow purple "waiting" look while no reading is live; and a test mode where a bpm typed into the serial monitor replaces the Bluetooth reading (`live` goes back). Confirmed 2026-11-10: with HeartCast running on the watch and iPhone (it needs the watch app installed, Health access allowed and the workout started from the watch), the board found "HeartCast-iPhon..." on its own, connected and printed a reading every 5 s with the web page's hues (72 bpm = hue 161). So the whole pipeline runs with no laptop in the data path: watch -> HeartCast -> Bluetooth -> ESP32 -> string. The typed-bpm test mode (80 bpm = hue 105) also checks out. Note for watch testing: readings come every 5 s, so the 5 s rolling average mostly holds a single sample and does little; the eased hue (`HUE_EASE`) is what keeps the color from jumping. A Polar sends once a second and the average then matters.
